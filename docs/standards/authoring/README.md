# 授權分層架構總覽

這份文件描述 agent-erp 授權模型的分層架構，以及目前的設計實踐。底下三份規範文件各自對應一個機制，撰寫新功能時依實際情況讀對應的那份：

- [`agent-skill-authoring.md`](./agent-skill-authoring.md) — Skill 層（操作權限）
- [`data-permission-extension.md`](./data-permission-extension.md) — 資料層：部門別欄位可見性（欄位權限）
- [`task-scoped-data-access.md`](./task-scoped-data-access.md) — 資料層：任務指派驅動的記錄範圍（記錄權限）

---

## 分層架構

授權分成三個獨立、正交的機制，各自回答不同層級的問題，不互相隱含：

| 機制 | 回答的問題 | 層級 | 管理單位 | 設定方式 |
|---|---|---|---|---|
| **Skill 權限** | 這個部門能不能使用這個動作？ | Action | `AgentProfile`（每個對應一個 skill，有 `id`/`domain`） | 集中管理：[#115](http://gitea.94peter.dev/Numax/agent-erp/issues/115) 部門可用 Skill 設定（二元授予） |
| **部門別欄位可見性** | 這個領域裡，哪些欄位對這個部門可見？ | Column | 各資料管理情境自己的範圍 | 不集中管理：由需要的情境各自新增 issue 設計 |
| **任務指派驅動的記錄範圍** | 這個使用者能碰到哪幾筆具體記錄？ | Row | 任務指派系統本身的行為 | 不是設定介面，是任務建立時宣告的 `referencedRecords`（見 [`task-scoped-data-access.md`](./task-scoped-data-access.md)） |

任何一個機制單獨成立，不代表另外兩個也成立——三者要分開判斷。

### 疊加判斷：三者是 AND，不是互相取代

實際執行一個會碰到資料的動作時，三個機制**同時**生效、互相不取代：

1. 先問 Skill 權限：這個部門有沒有這個動作的使用權？沒有就直接擋下，不用再看後面兩層
2. 再問記錄範圍：這個動作如果是由任務指派觸發，使用者能碰到的記錄有沒有限制在任務的 `referencedRecords` 內？有限制就只能碰那幾筆
3. 最後問欄位可見性：在能碰到的記錄裡，哪些欄位實際可見/可編輯？套用部門別的欄位規則

範例：業務人員被指派「聯繫客戶A，更新其近況」這個任務。他能操作客戶A（記錄範圍允許），前提是「客戶管理」這個 skill 本身對業務部門是開啟的（skill 權限允許）；如果客戶資料未來也有欄位可見性規則（例如業務部門看不到客戶的信用額度欄位），即使他能操作客戶A這筆記錄，信用額度欄位仍然不可見——**任務指派給的是「能碰到這筆記錄」，不是「無視欄位規則」**。

三者之間沒有優先順序上的覆蓋關係，只有「全部都要過」的 AND 關係。

## 設計實踐

這個分層不是預先規劃出來的架構，是從部門治理情境（#112-#116）的實際討論中收斂出來的：

1. 一開始嘗試用「資源類別 × 讀/寫矩陣」同時描述兩層，發現太粗——「能不能用」跟「能碰到哪些資料」是完全不同性質的問題，硬塞進一個矩陣會失真
2. 把「能不能用」抽出來變成 skill 權限，管理單位是 `AgentProfile`，因為 skill 清單會隨新情境持續增加，設計成需要分類（`domain`）跟搜尋的清單，而不是固定分類
3. 「能碰到哪些資料」刻意**不**做成集中機制——嘗試過兩種具體情境（任務指派驅動、部門別欄位可見性），發現本質差異很大，硬抽成一套通用框架只會變成最大公約數，於是改成由各資料管理情境自己負責，等真實需求出現才設計，不預先做

這個收斂過程本身就是這兩份規範文件存在的理由：往後新增 skill 或資料權限時，直接照這兩份文件的流程走，不用重新把這個收斂過程想一遍。
