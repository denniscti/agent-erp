# 任務指派驅動的資料存取

這份文件描述「任務指派驅動型」資料權限的設計原則（[`data-permission-extension.md`](./data-permission-extension.md) 第 3 節型態表列的其中一種型態），獨立成一份文件是因為它不是一個靜態設定、而是任務指派系統本身要內建的行為，牽涉到的設計決策比表格裡一行說明更多。

---

## 1. 機制定義

當一個任務被建立並指派給某個使用者時，若這個任務**引用了特定的業務資料記錄**（例如「聯繫客戶A，更新其近況」這個任務引用了客戶 A 這筆記錄），被指派的人就自動對該任務引用到的記錄有操作權——範圍**僅限**任務引用到的那幾筆記錄，不擴及該記錄所屬領域（domain）的其他記錄。

舉例：業務人員被指派「聯繫客戶A，更新其近況」這個任務，他能操作客戶A的資料，但不因此能操作客戶B、客戶C的資料——除非他也被指派了引用到客戶B、C的任務。

---

## 2. 跟 #115／資料權限矩陣的界線

這個機制**不**透過 [#115](http://gitea.94peter.dev/Numax/agent-erp/issues/115)（部門可用 Skill 設定）或任何部門層級的靜態資料權限設定來管理，原因：

- 它是**動態、跟著任務實例走**的，不是「這個部門永遠能/不能碰這個領域」這種靜態規則
- 存取範圍由任務建立時引用的具體記錄決定，不是由部門或使用者身份決定
- 它是任務指派系統本身內建的行為，不需要額外的權限設定介面讓管理者去配置

---

## 3. 現狀（已核對程式碼）

目前任務的建立介面 `createTaskAction(title, moduleId, assignee, parentTaskId)`（[`store.svelte.js`](../../../src/lib/store.svelte.js)）與底層 `create_task` 指令，**沒有任何欄位讓任務宣告它引用了哪些具體業務記錄**。這個機制目前沒有被任何現有任務型態使用，是為未來類似「聯繫客戶A更新近況」這種會引用具體記錄的任務情境預先寫下的設計原則，避免到時候忘記當初討論過的方向。

---

## 4. 未來落地時的設計方向

等真的有任務型態需要引用具體記錄時：

1. Task 資料模型需要新增一個引用欄位（例如 `referencedRecords: { domain: string, id: string }[]`），任務建立時宣告它關聯到哪些記錄
2. 對應的 `ToolHandler.execute()` 在執行會牽涉資料存取的動作時，要把存取範圍限制在該任務的 `referencedRecords` 列出的記錄，不能擴及整個 domain
3. 這個記錄級的範圍限制，是在 skill 權限（#115，能不能用這個動作）允許的前提之上**再加一層**限制，兩者疊加判斷，不互相取代

---

## 5. 跟既有文件的關係

- 屬於 [`data-permission-extension.md`](./data-permission-extension.md) 第 3 節型態表裡的「任務指派驅動型」，被排除在部門層級設定介面之外
- 不是 [`agent-skill-authoring.md`](./agent-skill-authoring.md) 的 `id`/`domain` manifest 欄位的一部分，不要把這個機制寫進 `AgentProfile` 裡
