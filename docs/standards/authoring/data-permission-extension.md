# 資料權限擴充管理規範

適用範圍：任何資料管理情境（例如客戶、供應商、未來的商品）需要限制「哪些部門/使用者能碰到哪些具體資料或欄位」時。這份文件跟 [`agent-skill-authoring.md`](./agent-skill-authoring.md) 是互補但正交的兩份規範——skill 權限管「能不能用這個動作」，這份文件管「這個動作能碰到哪些具體資料」。

---

## 1. 跟 Skill 權限的界線

[#115](http://gitea.94peter.dev/Numax/agent-erp/issues/115)「部門可用 Skill 設定」只管二元授予（部門有沒有某個 skill 的使用權），不處理資料本身的可見性或範圍。有 skill 的使用權不代表能碰到該 skill 涉及的所有資料——資料層面的限制是這份文件要處理的事，兩層完全獨立，不要互相假設對方已經擋住了什麼。

---

## 2. 不集中管理的原則

資料權限**不**集中在一個全域矩陣或共用機制裡設定。原因：不同資料領域的敏感維度完全不同（例如商品是欄位可見性、客戶可能是別的維度），硬塞進一個通用矩陣只會變成最大公約數，表達不出真正的業務需求，而且會重演部門治理（#112-#116）那一輪討論中已經排除掉的彎路。

資料權限**由各資料管理情境自己定義、自己負責**，用那個情境自己的 Who/Context/What/Why 去描述具體要擋的規則。

---

## 3. 設計時機：等具體需求出現才做

新增一個資料管理情境（例如 #117 客戶基本資料建檔）時，**不要**預先設計資料權限。等真的有「這份資料需要對某些部門隱藏/限制」的具體情境出現時，才為那個情境另開 issue 設計，避免為還沒出現的需求過度設計。

目前已知的具體情境型態，供之後遇到類似需求時參考命名與理解差異（不是強制套用的模板，新情境可能是全新的型態）。這張表是活的登記表，每次新增一個資料權限情境都要回來更新（見第 4 節的擴充流程）：

| 型態 | 說明 | 情境連結 |
|---|---|---|
| 任務指派驅動型 | 被指派處理某任務時，自動對該任務引用的具體資料有操作權，範圍僅限任務引用到的那幾筆。這是任務指派系統本身的行為，不需要額外的權限設定介面（已在 #115 的討論中確認排除）。設計原則詳見 [`task-scoped-data-access.md`](./task-scoped-data-access.md) | （無，排除於設定介面之外） |
| 部門別欄位可見性型 | 部門層級的靜態設定，決定在某個領域裡，哪些欄位對這個部門可見/不可見，套用在該領域所有記錄上（例如業務部門能看商品銷售資訊，看不到成本及貨源） | （尚無已實作情境，待商品管理情境落地後補上） |

---

## 4. 擴充方式

當某個資料管理情境真的需要資料權限時：

1. **先比對第 3 節的型態表**：這個需求符合表中既有型態嗎？符合就在該型態的「情境連結」欄位補上這張新 issue 的連結；不符合就新增一行描述新型態
2. 在該情境所屬的 milestone 底下新開一張 issue，用 Who/Context/What/Why 描述具體要擋的規則（跟 skill 情境的寫法一致）
3. 權限的判斷邏輯與儲存方式由這張 issue 自行設計，不必套用其他領域已經做過的模式——客戶的資料權限模式不必跟商品的模式一樣
4. **觸發門檻**：當同一個型態的「情境連結」累積到 2 個以上時，在該情境的 issue 裡標註「值得評估是否抽成共用機制」，交給架構角色評估是否要抽象——不要自己決定要不要抽，也不要在累積到門檻之前主動抽象

---

## 5. 跟既有文件的關係

- 跟 [#115](http://gitea.94peter.dev/Numax/agent-erp/issues/115)（skill 權限）互補但正交，不是它的延伸範圍
- 跟 [`agent-skill-authoring.md`](./agent-skill-authoring.md) 的關係：資料權限是資料管理情境自己的子題，不是 skill manifest（`id`/`domain`）的欄位，不要把資料權限規則寫進 `AgentProfile` 裡
